# Source review for repository cleanup

Date: 19 October 2026. Independent static review only: no implementation edits, build, solver run, or benchmark. Scope: `src/`, `include/bspai/`, root and CUDA CMake graphs, relevant specifications and the Phase 2B validation record. This review does not supersede the recorded numerical evidence. The FP64 baseline is specified by `docs/PHASE2A_ALGORITHM_SPEC.md`; the separate uniform FP32 extension is specified by `docs/EXPERIMENT2A_FP32_SPEC.md`.

## Findings, in priority order

1. **FP32 CSR duplicate order can change numerical input values.** `src/fp32_cpu.cpp:16` uses `std::sort` before summing duplicate coordinates, while the FP64 constructor uses `std::stable_sort` in `src/cpu.cpp:56` to retain input order. Float addition is order dependent. A cleanup that unifies constructors must explicitly choose and test an order; simply replacing the FP32 sort is a numerical change requiring an independently checked duplicate fixture and FP32 CPU/GPU downstream checks. Also, `Fp32CsrMatrix::Fp32CsrMatrix` at `src/fp32_cpu.cpp:15` forms `r+1` without the FP64 constructor's `size_t` overflow guard.
2. **FP32 CUDA SpMV does not enforce the FP64 input/output range contract.** `src/fp32_cuda_spmv.cu` checks vector length in `multiply` but does not reject nonfinite input or output, while `src/cuda_spmv.cu:120-136` does both. Its direct `std::size_t` to `int64_t` conversion and byte multiplications also lack the FP64 range checks. The FP32 wrapper accepts CSR properties less thoroughly than the FP64 one. Treat this as an API correctness and diagnostics gap, not evidence that an existing recorded run failed. Any guard fix needs focused finite/nonfinite and boundary tests and should retain the same accepted finite arithmetic.
3. **FP32 CPU SpMV can mask nonfinite input on empty rows.** `src/fp32_cpu.cpp:17` validates vector length but not values. An NaN or infinity in a component that no stored entry touches can produce a finite output and bypass the stated finite-input policy, unlike `src/cpu.cpp:73-82`. This also affects `fp32_refine_with_preconditioner` and diagnostics when they call `multiply`. The correction is input validation, with a sparse unused-column fixture; it should not change accepted finite cases.
4. **FP32 CUDA GMRES allocation count can overflow before its guard.** `src/fp32_cuda_gmres.cu` constructs `basis(fb(n*(cap+1)))`; `fb` checks only the already-computed product. The FP64 code uses checked products. Add a checked count multiplication before allocation if touching this path. Test the guard without allocating an enormous Krylov basis; do not use a changed iteration cap as the fix.
5. **FP32 GPU SPAI diagnostic mapping loses information.** In `src/fp32_cuda_spai.cu:97-117`, internal `zero_denominator` and `invalid_score` both map to public `numerical_failure`, and `score_history` retains only the latest fit. The latter is already disclosed in the handoff. A cleanup must not claim full fit history or precise status equivalence. Expanding the API is a separate behavior change requiring failure and multi-growth fixtures, public snapshot updates, and independent acceptance.
6. **The FP32 GPU SPAI specialization is compile-time text inclusion.** `src/fp32_cuda_spai.cu:48-72` defines `double` as `float`, redirects vendor APIs, and includes `cuda_spai.cu`. This is an intentional shared numerical body, but any edit to FP64 `cuda_spai.cu` changes FP32 behavior too. Keep both constructor targets and their tests in the same review/verification set. A templated refactor could improve maintainability, but it is a high-risk numerical rewrite, not a cosmetic cleanup. The score guard and accumulation seed macros are precision-specific and must remain so.
7. **The root/CUDA CMake files use file-existence gates for tests.** `CMakeLists.txt` and `cuda/CMakeLists.txt` conditionally omit many test targets when their source files are absent. Moving or pruning test sources can silently shrink CTest without a configure error. `cuda/CMakeLists.txt` also compiles the frozen Gate 3 reference and allocation audit only under `BUILD_TESTING`, and the FP32 CUDA SPAI target depends on `src/cuda_spai.cu` through direct inclusion. Record the expected target/test names before organization and compare the configured test inventory afterward.
8. **FP32 CPU implementation is highly compressed.** `src/fp32_cpu.cpp:6-29` holds CSR, QR, SPAI, GMRES, and IR in very long lines, limiting review and pinpoint diagnostics. Formatting and splitting by component may be safe if tokens, expression grouping, and evaluation order are preserved. Do this independently of any arithmetic or policy fix, and use source/binary comparison plus existing focused tests. The FP64 files already provide a clearer component layout but cannot be substituted wholesale because the precision contracts differ.

## Boundaries for a safe cleanup submission

The minimal buildable production set is `src/`, `include/bspai/`, root `CMakeLists.txt`, and `cuda/CMakeLists.txt`; the CUDA graph refers to both source and include through `../`. Keep `tests/` with its `tests/reference/cuda_spai_gate3.cu`, `tests/cuda_spai_allocation_audit.cu`, and Decimal80 checkers for independently reviewable correctness. Build scripts in `scripts/` carry machine-specific toolchain setup and benchmark locking; matrix inputs, manifests, and `results/` sidecars support the recorded evidence. `docs/PHASE2A_ALGORITHM_SPEC.md`, `docs/EXPERIMENT2A_FP32_SPEC.md`, `docs/PHASE2B_VALIDATION_RECORD.md`, `PROJECT_HANDOFF.md`, `CODEBASE_GUIDE.md`, and `PAPER_INDEX.md` are the necessary contract/evidence entry points. None of the current dirty/untracked source, scripts, inputs, or evidence is established as disposable merely because it is untracked.

For organization-only changes, verify both CMake configurations and their configured CTest inventories, then run the existing CPU and CUDA CTest suites. For any numerical source change, independently compare the affected precision's CPU/GPU statuses, construction patterns and coefficients, fixed-`P` GMRES histories, original residuals, and final backward errors against preserved snapshots and Decimal80 checks. Retain the documented FP64 singular-status divergence and FP32 limitations; do not normalize results by changing tolerances or benchmark methodology. The existing MSVC CPU Release CTest 1/4 wider-oracle limitation remains relevant when interpreting a Release run. No new numerical or performance claim follows from this static review.
