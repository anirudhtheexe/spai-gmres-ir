# Phase 2B Gate 3: GPU SPAI construction report

11 October 2026. Correctness-first implementation and bounded independent validation complete. Stop at Gate3 for parent handoff; no later stage is approved here. No BSPAI bucketing, mixed precision, performance benchmark or novelty claim is included.

## Source basis and intended change

The unchanged [Phase2A executable specification](PHASE2A_ALGORITHM_SPEC.md), CPU `src/spai.cpp`, Carson–Khan [P1 Algorithm2.1/section4](https://arxiv.org/pdf/2202.10204v2), and the [published BSPAI paper](https://link.springer.com/article/10.1007/s00366-025-02187-z) define the baseline. This stage changes numerical execution backend and scheduling, not identity initial patterns, scaling B=A^T D/P=N^T D, restricted scoring, epsilon<=, growth/refit budgets, ascending tie order, bounded32u score clamp, exact-zero rank guard or failure acceptance. GPU native QR/triangular arithmetic can round differently from the CPU Householder implementation; bitwise histories/pattern equality are not promised at numerical boundaries.

Independent least-squares columns and GPU construction already have prior art. [Wang–Li–Gao2021 sections2–3](https://www.tbench.org/single/1-9.pdf) explicitly describe independent SPAI columns and GPU submatrix/QR/triangular/assembly work; that paper uses a static pattern and MPI/multi-GPU framework, not this adaptive Carson–Khan algorithm. Its decision-tree kernels, padded problems, BiCGSTAB stopping and reported speedups are not copied or reproduced. This single-GPU host-controlled implementation is a project realization, not a verified novel parallel-SPAI contribution.

[Official cuSOLVER documentation](https://docs.nvidia.com/cuda/cusolver/index.html) supplies `Dgeqrf`/`Dormqr`, column-major storage, device info, stream, workspace and deterministic/native math controls; [cuBLAS](https://docs.nvidia.com/cuda/cublas/index.html) supplies `Dtrsv` and its lack of singularity checking. Research confirmed the exact mapping below before implementation.

## GPU numerical work and parallel scheduling

`cuda_construct_spai` accepts canonical CPU CSR and existing SpaiOptions. GPU kernels compute original-row maxima/reciprocal scaling and B=A^T D, with unchanged nonzero/range/diagonal guards. For each sorted J and shadow I, GPU gathering produces an **unpadded** column-major m-by-q matrix B(I,J), m=|I|, q=|J|, lda=m. Actual dimensions vary independently across columns and growth rounds.

Each fit performs `Dgeqrf(m,q)` then `Dormqr(LEFT,TRANSPOSE,m,1,k=q)` on the restricted identity RHS, then `Dtrsv(UPPER,NONTRANSPOSE,NONUNIT,q)` on the first q transformed RHS entries. QR workspace and Q-application workspace are queried separately in double elements; their maximum is reused only in sequence on the same stream. QR overwrites its reduced buffer, but immutable GPU B remains unchanged: original reduced entries are re-read from B for residual/conditioning calculations, never read as if the overwritten QR factors were original data. API statuses/device info, all returned factors/tau/transformed RHS, exact-zero R diagonals and solved coefficients are checked. QR info is not rank certification. No pivoting, normal equations, regularization, structural fallback or numerical-rank tolerance is added.

A pool of min(n,8) independent nonblocking streams/solver+BLAS handles bounds reduced workspace memory. All slot metadata/workspaces are prepared before a batch launches. Every batch submits all independent gather/QR/Q-application commands before the first explicit host result collection; after pivot validation, every usable slot submits its triangular/residual/scoring work before result collection. Separate streams own disjoint mutable buffers/columns and share read-only B. Telemetry records streams_created, max_fit_batch, parallel_fit_batches, qr_submissions and max_qr_submissions_before_collection. This verifies independently issued parallel column work, **not measured hardware kernel overlap or a speedup**; vendor-internal synchronization is not traced. Host adaptive scheduling alone is not represented as GPU numerical parallelism.

GPU residuals are recomputed in ascending pattern order. Both reduced/full residual2 norms use the same safe-scaled strategy validated in Gate1, avoiding the pinned cuBLAS subnormal norm discrepancy; no cuBLAS norm fallback is used. GPU candidate threads compute restricted dot/denominator and the unchanged32u bounded score clamp. `cuda_evaluate_spai_score` exposes the **same device score routine** for direct exceptional/boundary tests. A failed fit's status is checked before score kernels read its residual/diagnostics. GPU kernels commit only a completed fitted column into N, and assemble P[k,j]=N[j,k]*d[j], preserving the right-side D and assembly underflow/nonfinite guards.

Every column completes independently; the smallest failing column determines the overall construction status after all submitted work completes. Computed-zero pivots produce rank_deficient; small finite pivots are retained and diagnosed. Failed construction never supplies P to GMRES/IR. Different backends can report different failure statuses/partial histories for unsupported singular input; neither CPU nor GPU globally certifies nonsingularity.

## Native arithmetic, ownership and staging limitations

cuSOLVER explicitly sets/queries `CUSOLVER_DETERMINISTIC_RESULTS` and `CUSOLVER_DEFAULT_MATH`; cuBLAS explicitly sets/queries PEDANTIC_MATH, HOST scalar mode and atomics-not-allowed. The reproducible script uses CUBLAS_EMULATE_DOUBLE_PRECISION=0. Typed D APIs/native binary64 are used throughout; no emulation or low-precision mode is requested. Custom kernels use --fmad=false and no fast math; host metadata/mean scoring uses /fp:strict. These flags do not dictate prebuilt library reductions/FMA, and determinism does not imply CPU/GPU bitwise equivalence.

Research additionally verified cuSOLVER's floating-point-emulation documentation: emulation configuration acts only in an emulation-enabled math mode, and cuBLAS emulation-enable environment variables do not affect cuSOLVER's internal handles. Explicit DEFAULT_MATH readback is the documented non-emulation setting; no separate cuSOLVER emulation-enable environment variable is specified. This does not assert absence of Tensor Core use: DEFAULT_MATH permits Tensor Cores where applicable while retaining the requested D-routine precision.

All CUDA streams/memory and cuSOLVER/cuBLAS handles have exception-safe ownership, including partial slot construction. Host-copy lifetimes are synchronized explicitly; teardown drains streams before buffers disappear. Runtime/library/allocation exceptions are checked and never trigger CPU numerical fallback. Numerical construction failures are named statuses with completed-fit diagnostics.

**Remaining CPU staging:** canonical CSR input and final CSR packaging; downloaded B support for sorted J/I/candidate-set construction; per-fit metadata upload; device info/finite/pivot/residual/coefficients/score/status download; CPU mean/sort/tie selection and outer stopping decisions; final dense N/P download and canonical CSR formation. `uploads`, `downloads`, `upload_bytes` and `download_bytes` count application-issued copies including scalars/metadata, not vendor-internal traffic. This is hybrid host-controlled GPU construction, not fully device-resident adaptive control.

**Memory/scalability limit:** B/N/P are dense n² device staging arrays, plus up to8 n² reduced QR buffers, queried workspaces and O(n) slot arrays. Output remains sparse canonical CSR, but this is **not a scalable sparse-memory construction**. Legacy solver dimensions are checked against INT_MAX, allocation/index products use checked host sizes, and unavailable GPU memory produces an explicit checked exception. No arbitrary numerical n threshold or CPU fallback is invented. CPU pattern search and dense diagnostic transfers are deliberately unoptimized.
