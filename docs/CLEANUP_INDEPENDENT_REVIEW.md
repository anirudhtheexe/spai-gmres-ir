## Actionable findings

1. **Submission packaging currently fails if run before the planned README exists.** `scripts/package_submission.py:10,30` unconditionally reads `README.md`, which was absent at this review. The parent reports it is planned. Because line 26 opens the output ZIP in `w` mode first, this failure also truncates any earlier successful submission ZIP at that path. Preflight all mandatory files, write a temporary ZIP, verify it, then replace the destination. The script should reject an absent required file before opening the destination. Verify the final package by extracting to a fresh directory and configuring CPU and CUDA builds there.
2. **The source-only package omits project role definitions and research inputs.** The allowlist excludes `.codex/agents/*.toml`, `benchmarks/*.json`, `data/`, `results/`, and root experiment reports. That may be intentional for a compact Teams source package, but `AGENTS.md` asks readers to use the local roles, and bundled benchmark/validation scripts refer to omitted cases and data. Clearly state the package's scope in README. If it must be a stand-alone research reproduction, add the requisite role definitions, case manifests, input matrices/provenance, and selected evidence, or supply the verified research archive beside it. The current package does include `tests/fixtures/*.mtx` via its suffix allowlist.
3. **Archive verification accepts duplicate ZIP member names.** `scripts/research_archive.py:37` compares sets of member names, so a ZIP with extra duplicate entries passes the inventory check. `ZipFile.open(name)` resolves one of the duplicates; another reader may select differently. Compare member counts as well as unique names and manifest entries. The current archive was checked independently through ZIP metadata: 1,427 members (1,426 files plus manifest), all names unique, with 1,426 manifest records totaling 1,846,708,788 original bytes. All 61 explicit selection entries matched at least one archived path. This is an improvement for future archives, not an observed duplicate in this one.
4. **Archive pruning has a time gap between checking and unlinking.** `scripts/research_archive.py:77-89` hashes the entire loose source set, then deletes each file without checking its hash again. A writer that changes a file after the precheck could have its new bytes deleted. Before pruning, require no active benchmark, profiler, solver, or other writer; ideally rehash each file immediately before unlinking and abort on any change. The parent reports no benchmark is running. Keep the created ZIP and its verified manifest available as the restore source after pruning.
5. **Archive path checking relies on resolved targets.** `safe_path` permits an absolute path inside the root despite the documented project-relative selection format, and it resolves an in-root symlink selection to its target. The current `safeguards/cleanup_20261019/archive_selection.json` uses relative ordinary paths, so this does not invalidate that archive. If the archive tool will be reused with other selections, reject absolute paths, traversal components, and symlink components before resolving; retain the existing root containment check.
6. **The Windows CPU script runs only two of five CPU CTest targets.** `scripts/build_windows.cmd` filters to `cpu_core_tests|fp32_cpu_tests`; the three FP64 solver suites are omitted because MSVC `long double` cannot satisfy their wider-oracle assertions, and the separate Decimal80 checker is invoked afterward. This is a documented toolchain split. README and test reporting should name the two CTest targets plus the Decimal80 gate, and separately show all five CPU CTest targets on a toolchain with a wider `long double`. Do not present the Windows script's CTest output alone as a full 5/5 CPU run.

## Build and CLI assessment

The consolidated CMake dependency graph retains FP64 CPU, FP32 CPU, and separate FP64/FP32 CUDA libraries. `cmake/CudaTargets.cmake` keeps the Gate 3 reference and allocator audit in `BUILD_TESTING` only. `src/fp32_cuda_spai.cu` still directly includes `cuda_spai.cu`; edits there require both constructor suites. The standalone `cuda/CMakeLists.txt` is a compatibility entry point and deliberately disables the original CPU wide-oracle CTest suites. The new `solver_main.cpp` delegates arithmetic to existing precision-specific APIs; its FP32 CLI parses Matrix Market through the binary64 CSR reader and then rounds stored entries to float with range and underflow guards. That input-conversion convention should be stated in README and retained in CLI checks. The CLI returns `0` only on convergence, `1` on solver failure, and `2` on input error; host-side smoke tests remain necessary because the sandbox run never started.

## Focused immutable guard checks

The parent reports a baseline reproduction of the FP32 unused-column NaN issue and is adding only finite-input/output and size-overflow guards. For an independent check, retain the original baseline library and source hash, build the changed library separately, and feed both the same immutable fixtures. A `1 x 2` FP32 CSR row with only column 0 stored and `x[1]=NaN` isolates unused-column input validation; a matching finite vector confirms unchanged accepted arithmetic. Include `Inf` and output-overflow probes for CPU and CUDA SpMV, with the GPU run on the validated host. For constructor range checks, call `Fp32CsrMatrix(SIZE_MAX, 1)` and require a named exception before allocation. For CUDA GMRES basis-size overflow, use `n` and cap values whose `n*(cap+1)` overflows `size_t`, and verify rejection before any allocation or kernel launch; a narrow validation hook or checked helper may be needed because an actual CSR of that dimension is impractical. These are straightforward input/range guards, not changes to the frozen QR, scoring, GMRES, IR, tolerance, or FP32 arithmetic policy. Preserve finite-case bit payloads and Decimal80 acceptance as the regression criterion.
